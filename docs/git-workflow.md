# Git-воркфлоу: форк и актуальность кода

## Как устроен репозиторий

Этот проект — **форк** (`we2go/crm-compai`) репозитория
[`trycompai/crm`](https://github.com/trycompai/crm) (родитель). Мы дорабатываем
код под себя в своём форке, а от родителя регулярно подтягиваем обновления.

| Remote | URL | Назначение |
| --- | --- | --- |
| `origin` | `git@github.com-tl-tm:we2go/crm-compai.git` | **Наш форк** — сюда мы пушим |
| `upstream` | `https://github.com/trycompai/crm.git` | **Родитель** — отсюда берём обновления |

Проверить remotes:

```sh
git remote -v
```

## SSH-доступ

Для пуша в GitHub используется SSH-ключ `~/.ssh/github_tl-tm` (аккаунт `we2go`).
В `~/.ssh/config` он описан алиасом `github.com-tl-tm`:

```
Host github.com-tl-tm
  HostName github.com
  User git
  IdentityFile ~/.ssh/github_tl-tm
  IdentitiesOnly yes
```

Поэтому `origin` указан как `git@github.com-tl-tm:we2go/crm-compai.git` — так
git подхватывает нужный ключ без пароля.

## Обычный цикл работы (ежедневный)

Работаем и пушим **в свой форк**:

```sh
git add -A
git commit -m "feat: ..."
git push origin release
```

`origin` — это наш репозиторий, в него можно пушить напрямую.

## Синхронизация с родителем

Когда в `trycompai/crm` появляются новые коммиты (фиксы, фичи, релизы),
подтягиваем их в наш форк:

```sh
# 1. Скачать новые ссылки из родителя
git fetch upstream

# 2. Влить изменения родителя в текущую ветку
git merge upstream/release

# 3. Отправить обновлённый форк
git push origin release
```

### Merge или rebase?

Для ветки `release` используем **merge**, а не rebase:

- `merge` не переписывает историю и безопаснее, когда репозиторий общий;
- история остаётся понятной: наш форк = родитель + наши коммиты.

Rebase оправдан только для локальных фича-веток перед PR, когда хочется
линейную историю.

### Что делать при конфликтах

1. `git merge upstream/release` — git остановится и покажет конфликтные файлы.
2. Открой конфликты (`<<<<<<<`, `=======`, `>>>>>>>`), оставь нужный вариант:
   - правки родителя — если берём их фичу/фикс;
   - наши правки — если это наша кастомизация.
3. Сохрани файлы, затем:
   ```sh
   git add -A
   git merge --continue
   git push origin release
   ```

Чем чаще подтягиваешь родителя, тем меньше и проще конфликты.

## Как правильно отдавать изменения наверх (в родителя)

`origin` и `upstream` — это разные репозитории. Мы не пушим в родителя
напрямую. Наши изменения попадают туда только через **Pull Request**.

По правилам родителя (`CONTRIBUTING.md`):
- ветки `main` и `release` в родителе двигаются **только через PR**;
- PR из форка открывается с `--base main` (не `release`).

То есть:
- **общие** фиксы/улучшения → PR из `we2go/crm-compai` в `trycompai/crm` (base `main`);
- **личные** кастомизации под нас → остаются только в нашем форке, никуда не отправляются.

## Как избежать расхождений и конфликтов

1. **Свои кастомизации держи в отдельных местах** — меньше пересечений с
   родителем, меньше конфликтов при merge.
2. **Подтягивай родителя регулярно** (например, раз в неделю), а не раз в
   полгода.
3. **Не переписывай ядро родителя без нужды** — правь точечно.
4. Перед большим merge убедись, что рабочее дерево чистое:
   ```sh
   git status --short
   ```

## Шпаргалка команд

| Действие | Команда |
| --- | --- |
| Посмотреть remotes | `git remote -v` |
| Забрать обновления родителя | `git fetch upstream` |
| Влить родителя | `git merge upstream/release` |
| Запушнить в форк | `git push origin release` |
| Посмотреть, на сколько мы впереди/позади | `git rev-list --left-right --count origin/release...upstream/release` |
| Разрешить конфликт после merge | `git add -A && git merge --continue` |
| PR в родителя | `gh pr create --repo trycompai/crm --base main` |

## Проверка актуальности

```sh
git fetch upstream
git rev-list --left-right --count origin/release...upstream/release
```

Вывод `1  0` означает: наш форк на 1 коммит впереди родителя и не отстаёт —
всё актуально. Число справа больше нуля — пора делать `git merge upstream/release`.
